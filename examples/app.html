screenferry — test app

A basic manual test harness — not part of the library, not published. Uses the negotiated API (preferredBackend), so it exercises qrLtBackend, cimbarBackend, and the header-frame auto-detection between them.

When checked and backend is cimbar, every section below uses the pinned, non-negotiated path (encodeToFrames(file, { backend: cimbarBackend }) / new ReceiverSession(callbacks, cimbarBackend).start(video, { rawFrames: true })) instead of preferredBackend + NegotiatingReceiverSession. This removes NegotiatingReceiverSession.switchToRawFrames()'s camera stop/restart handoff as a variable — a handoff this project's own docs note is un-exercised against real camera hardware. If cimbar works pinned but not negotiated, the bug is in that handoff, not the cimbar codec itself.

Speed tuning notes (qr-lt)

qr-lt's throughput is roughly fps × fragmentSize bytes/second, bounded by how fast the receiver can actually scan and decode. Two knobs, both above:

  • fps — DisplayDriver's display rate. Higher sends more frames/second, but the receiver's camera and decode loop need to keep up, or frames just get skipped without being scanned (no benefit, same failure mode as raising it too far).
  • fragmentSize — bytes packed into each QR frame. Bigger means fewer total frames needed, but a denser, harder-to-scan QR code — reliability drops if the receiver's camera can't resolve it clearly (resolution, distance, focus, motion blur all matter more as this grows). Leave blank for the library's own tuned default (~580 bytes, chosen for reliable scanning at ECC level L / QR version ≤ 20 — see qr:capacity in package.json if you want to compute a different ceiling).
  • scanHz — how often the receiver samples a camera frame for decoding. Should track roughly 2× the sender's fps (the default) — much lower and it may miss frames as they change; much higher just burns CPU decoding the same still-displayed frame repeatedly, with no throughput benefit.

Beyond these knobs: QR ECC is already at the library's minimum overhead level (L), so there's no further redundancy to trade away. On the physical/environmental side — screen brightness/contrast, camera autofocus lock, holding distance/angle steady, and reducing motion blur — all matter more than they might seem, and are usually a bigger lever on real-world reliability (which is what lets you safely raise fps/fragmentSize in the first place) than any of the code-level knobs above.

Cimbar-specific notes

Cimbar packs far more information per unit area than QR (a fixed 112×112-cell grid across the whole frame at every frameSize, vs. QR's much larger, sparser modules), so it's far more sensitive to things QR mostly tolerates:

  • On-screen code size. The sender canvas below now displays at its native resolution instead of being squashed into a small box — that squashing was previously forcing an ugly, aliased downscale of Cimbar's fine grid (nearest-neighbor scaling of a 1024×1024 render into a few hundred CSS pixels), which likely made frames flatly unreadable regardless of the camera. Resize it further if useful (see section 2), and hold the receiving camera close enough that the code fills a good fraction of the frame.
  • Camera capture resolution. Without an explicit constraint, browsers often negotiate a low resolution (e.g. 640x480) that's plenty for QR but starves Cimbar of pixels per cell. Camera/Scanner now request 1920x1080 as an ideal by default — section 3 shows the actual negotiated resolution once scanning starts, so you can tell whether the camera is genuinely giving you low resolution vs. the code just being displayed too small.
  • frameSize is a resolution knob, not a density knob. Cimbar's mode B grid is always 112×112 cells no matter what frameSize you pick — shrinking it to e.g. 512 does not produce fewer, bigger, easier-to-scan cells; it renders the exact same 112×112 grid into fewer physical pixels, giving the camera less to work with per cell. If anything, try raising it above the 1024 default (device performance permitting) rather than lowering it, and lean on a larger on-screen display size / closer camera distance as the main reliability lever instead.
